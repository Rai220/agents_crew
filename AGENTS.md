# AGENTS.md — команда ИИ-сотрудников

Это общий каталог команды. Рабочего кода здесь нет: здесь устройство сотрудников,
навигация по ним и шаблон для найма нового.

- **Что это и зачем** — [`README.md`](README.md)
- **Кто есть в команде** — [`CREW.md`](CREW.md)
- **Шаблон нового сотрудника** — [`crew_template/`](crew_template/)

Если тебя запустили в этом каталоге — ты не сотрудник, а администратор команды:
правишь шаблон, нанимаешь новых, обновляешь навигацию. За рабочими задачами
сотрудников запускают из их собственных каталогов.

---

## 1. Модель

**Сотрудник — это каталог, а не промпт.** У каждого свой домашний каталог
`crew_<имя>/` со своими правилами, памятью и журналом.

```
crew_<имя>/
├── AGENTS.md              # правила и личность — единственный источник правды
├── CLAUDE.md -> AGENTS.md # симлинк для харнессов со своим именем файла
├── README.md
├── memory/                # что сотрудник знает между запусками
│   ├── MEMORY.md          # индекс, читается в начале каждого запуска
│   ├── projects/          # один файл на проект
│   ├── lessons.md         # обратная связь создателя и выводы из провалов
│   └── stack.md           # окружение, доступы, стенды
└── journal/               # YYYY-MM.md, хронология работы
```

Из этого следуют три свойства:

- **Переносимость.** Сотрудник не привязан к харнессу и не зависит от его фич.
  Всё состояние — в файлах, в обычном markdown.
- **Версионируемость.** Личность и память лежат в git: видно, как менялись правила
  и когда сотрудник что узнал.
- **Изоляция.** У каждого своя память. Общего хранилища нет намеренно: смешивание
  контекстов ML и бекенда делает хуже обоим.

Отсюда же главное ограничение: **между запусками переносится только то, что записано
в файлы**. Ничего из контекста сессии не выживает.

---

## 2. Как запустить сотрудника

Сотрудник запускается любым CLI-харнессом с рабочим каталогом в его доме:

```sh
cd {{CREW_ROOT}}/crew_steve

claude           # Claude Code
codex            # Codex
free-code        # free-code
deepagents       # deepagents
kimi             # Kimi CLI
```

**Правило подхвата правил.** `AGENTS.md` — де-факто стандарт и источник правды.
Харнессы, которые ищут файл под своим именем, обслуживаются симлинком (`CLAUDE.md`
уже есть; для нового харнесса — `ln -s AGENTS.md <ИМЯ>.md`).

Если харнесс не подхватывает ничего автоматически — скажи это первым сообщением:

```
Прочитай ./AGENTS.md и ./memory/MEMORY.md, дальше действуй по ним.
```

**Одноразовый запуск без диалога** — там, где харнесс это умеет:

```sh
cd {{CREW_ROOT}}/crew_lora && free-code -p "посмотри results/ и скажи, есть ли регресс"
```

### Работа в чужом проекте

Сотрудник — не хозяин проекта: он приходит в него на время задачи. Два способа:

1. **Из дома, с абсолютным путём** (память подхватится сама):
   ```sh
   cd {{CREW_ROOT}}/crew_steve && codex
   > разберись, почему стриминг рвётся в {{PROJECTS_ROOT}}/<проект>
   ```
2. **Из проекта, с явной ссылкой на дом** (когда важны локальные правила проекта):
   ```sh
   cd {{PROJECTS_ROOT}}/<проект> && claude
   > Ты — Стив. Прочитай {{CREW_ROOT}}/crew_steve/AGENTS.md и
   > {{CREW_ROOT}}/crew_steve/memory/MEMORY.md, дальше действуй по ним.
   ```

В обоих случаях **локальные правила проекта приоритетнее правил сотрудника** во всём,
что касается стиля кода, тестов и процессов.

## 3. Как поручать работу

- **Один сотрудник — одна специальность.** Задача не по профилю выполняется хуже и
  засоряет память нерелевантным. Кому что — в [`CREW.md`](CREW.md).
- **Параллельно можно.** Два сотрудника в разных терминалах — нормально, пока они не
  правят одни и те же файлы. Один репозиторий на двоих одновременно — источник
  конфликтов.
- **Обратная связь стоит дороже задачи.** Поправка «так не делай, потому что…»
  попадает в `memory/lessons.md` и работает во всех следующих запусках. Молча
  переделанная за сотрудника работа не учит никого.
- **В конце запуска — попроси записать память.** Хороший запуск, из которого ничего
  не записано, повторится с нуля.

### Обмен знаниями между сотрудниками

- Память соседа **читать можно** (`../crew_<имя>/memory/`), **писать в неё — нельзя**.
- Полезный чужой урок сотрудник переносит к себе в `memory/lessons.md` со ссылкой на
  источник, а не ссылается на чужой файл из своих правил: чужой файл переименуют.
- Знание, полезное всем, — не в `crew_template/`, а в правила конкретных сотрудников.
  Шаблон меняется только когда меняется само устройство сотрудника.

### Консультация: сотрудник как субагент

Сотрудник может спросить совета у соседа сам, запустив харнесс в его каталоге:

```sh
cd {{CREW_ROOT}}/crew_<имя> && claude -p "<вопрос со всем контекстом>"
```

Вызванный поднимается со своими правилами и своей памятью и возвращает текстовый ответ.
Границы, прописанные всем в `AGENTS.md`:

- **Консультация, а не делегирование.** Вызванный читает свою память и код, может
  запускать проверочные команды, но файлы не правит и не коммитит. Правки делает тот,
  кого запустил человек, — иначе двое агентов в одном репозитории дадут конфликты.
- **Глубина 1.** Вызванный консультантом сам третьего не зовёт: отвечает в своей части и
  говорит, к кому идти дальше. Идти по цепочке дальше можно только с явного разрешения
  в задаче — иначе цена запуска непредсказуема.
- **Ответ соседа — мнение, а не факт.** Спрашивающий проверяет его у себя и записывает
  полезный вывод в свою `memory/` со ссылкой на источник.
- Сотрудник обязан сказать, что зовёт соседа, и пометить, чей ответ он передаёт.

## 4. Как нанять нового

```sh
cd {{CREW_ROOT}}
cp -R crew_template crew_<имя>
cd crew_<имя>
```

Дальше:

1. **Заполнить плейсхолдеры** `{{ИМЯ}}`, `{{РОЛЬ}}`, `{{КАТАЛОГ}}` и удалить
   HTML-комментарии в `AGENTS.md`, `README.md`, `memory/*.md`.
2. **Написать раздел 1 «Кто ты»** — специализация конкретно, чтобы было понятно, какие
   задачи его, а какие соседа.
3. **Написать раздел 4 «Регламент по специальности»** — главная ценность сотрудника.
   Не пожелания, а правила: что проверять до начала, какие ошибки типовые, что нельзя
   делать без подтверждения, как отчитываться. Разделы 2, 3, 5, 6, 7 — общие, их без
   причины не трогать. Исключение — «Работа с другими сотрудниками» в разделе 2:
   там перечислены соседи и их специальности, это надо заполнить.
4. **Проверить симлинк**: `ls -la CLAUDE.md` → должен вести на `AGENTS.md`.
5. **Заполнить `memory/stack.md`** — окружение, доступы, стенды, ограничения. Отдельно
   проговорить договорённость про секреты.
6. **Завести первые заметки в `memory/projects/`** — по файлу на проект, ссылки в
   `memory/MEMORY.md`. Сотрудник без заметок по проектам ничем не лучше чистого чата.
   Рабочий размер скоупа — 3-10 проектов; часть из них будет общей с соседями, и это
   нормально.
7. **Добавить строку в [`CREW.md`](CREW.md)** — иначе сотрудника не найдут ни человек,
   ни другой агент. Если у новичка есть общие проекты с кем-то, дописать их в таблицу
   скоупов и сказать, кто в них за что отвечает.
8. **Дописать новичка в раздел «Работа с другими сотрудниками» уже нанятым** — иначе
   они о нём не узнают и за консультацией не придут.

**Держать `AGENTS.md` компактным.** Он читается целиком при каждом запуске: раздутый
файл вытесняет из контекста то, ради чего запуск затевался. Новое знание по умолчанию
идёт в `memory/`, а не в правила. Лор и детали персоны — не идут никуда.

## 5. Правила, общие для всех

Продублированы в `AGENTS.md` каждого сотрудника — здесь они как справка о том, на что
можно рассчитывать:

- Не коммитить без явной просьбы. Push, force-push, PR — только по прямому запросу.
- Не коммитить секреты, датасеты, веса, персональные данные. `git add .` не
  использовать — файлы перечислять явно.
- Перед дорогой или необратимой операцией — спросить, назвав цену и время.
- Не выдавать предположение за факт. «Не знаю» — валидный ответ, дальше идёт проверка.
- Проверять результат самому перед сдачей. «Должно работать» — не сдача.
- Пути в памяти и журнале — абсолютные, даты — абсолютные (`2026-08-13`).
- `python3`, не `python`.

---

## 6. Границы этого репозитория

- Здесь нет кода вообще, только устройство команды и память сотрудников. Код решает
  прикладную задачу, а значит живёт в проекте, а не тут.
- Приложения для разговора с командой тоже нет и не нужно: сотрудника поднимает
  харнесс, а интерфейс к нему — терминал.
- `crew_template/` — шаблон, а не рабочий сотрудник. Правки в него не долетают до уже
  нанятых: если меняется общее правило, его надо разнести по их `AGENTS.md` руками.
